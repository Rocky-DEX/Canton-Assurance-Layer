## Abstract

`dpm explain` turns a rejected Canton submission into a structured, actionable diagnosis:
the phase that failed, the Canton error code with the Foundation's own explanation and
resolution, the facts extracted from the cause (assertion message, missing authorizers,
template, choice, contract ids, `failWithStatus` error id), whether a referenced contract
is active, archived or unknown to the participant, whether a retry can help, and concrete
next steps. It works on the rejection returned by `prepare` (before submission), on a
completion, on the JSON error body, or on the log line a client printed. The error
catalog — 228 codes regenerated from Canton's sources per release — and the diagnosis JSON
are published as open, versioned public goods so `dpm trace`, DPM Debug, CI runners and
wallets can consume them. A working, tested implementation is delivered with this
proposal; the grant funds a labelled rejection corpus with measured precision, DPM
packaging, an integration contract, and adoption by at least three independent
organisations.

## Specification

### 1. Objective

A rejection reaches a Canton developer as an error code and a free-text `cause`, and the
public error reference is a 2.x-era snapshot. Walnut's approved `dpm trace` (#327)
renders completion status and error details; Tenderly's failure analysis (#481) lives in a
commercial dashboard; the open Failure-Classification Engine (#297) was closed for
portfolio reasons after reviewers had converged on the bar: open taxonomy, measured
precision on a labelled corpus, a stable integration contract, `dpm` packaging.

Outcome: one command or API call turns any Canton rejection into a diagnosis a developer
can act on and a JSON other tools can consume, with the underlying error knowledge kept
current per Canton release as an open artifact.

Single objective: failure explanation. Cost estimation is a separate proposal
(`2026-09-Rocky-dpm-fee-estimator.md`); visualisation and diffs are Walnut's.

### 2. Implementation Mechanics

**Inputs.** A `JsCantonError` body from the JSON Ledger API; the same body wrapped in an
HTTP-client error string; a gRPC-style line (`CODE(category,correlation): cause`); a
completion payload; or a live `prepare` of a command (`canton-sim simulate`), which yields
the identical rejection the real submission would have produced, with no submission and
read-only rights.

**Catalog.** `canton-error-catalog.json`: for each Canton error id, the category,
explanation, resolution and provenance. Generated by a script from the `@Explanation` /
`@Resolution` annotations in Canton's sources (202 codes from `release-line-3.4`:
command execution, consistency, request validation, local verdicts, transaction
processing, sync service, sequencer, common, topology, admin), plus 21 codes from the
Daml error reference whose definitions have not moved and 7 hand-written routing and
authorization entries marked `manual` for verification. Regeneration for a new Canton
release without manual edits is a Milestone 4 acceptance criterion.

**Classifier (implemented, `crates/canton-sim-diagnose`).** Deterministic and pure:
phase (auth · request · interpretation · Daml authorization · routing · sequencing ·
confirmation · participant) by code and prefix; per-code specialisation for the codes
developers hit most (`UNHANDLED_EXCEPTION` with exception type and message,
`DAML_FAILURE` with error id, `TEMPLATE_PRECONDITION_VIOLATED`, `DAML_AUTHORIZATION_ERROR`
with required / given / missing authorizers, `CONTRACT_NOT_FOUND` / `CONTRACT_NOT_ACTIVE` /
`LOCAL_VERDICT_*`, `NO_SYNCHRONIZER_FOR_SUBMISSION`, `PACKAGE_NOT_VETTED_BY_RECIPIENTS`,
`SEQUENCER_NOT_ENOUGH_TRAFFIC_CREDIT`, backpressure and deduplication codes, request-shape
errors including the single-command limitation of `prepare`); extraction of template,
choice, contract ids, parties, package and synchronizer from the cause; retryability from
the Canton category and `definiteAnswer`; hints on whether traffic was consumed.

**Contract-state lookup.** For contract-related rejections, `/v2/events/events-by-contract-id`
for the acting parties distinguishes *active*, *archived at offset N* and *never seen by
this participant*, and the hint changes accordingly (successor lookup, disclosed contract,
wrong party set).

**Output — the integration contract.** A versioned `Diagnosis` JSON: `code`, `phase`,
`category`, `title`, `summary`, `explanation`, `resolution`, `extracted`, `hints`,
`retryable`, `definite_answer`, `contract_states`, `catalog_source`, and the parsed error.
Milestone 3 freezes it as a semver'd schema with a reference adapter for `dpm trace`.

**Corpus and metrics (Milestone 2).** A frozen, labelled rejection corpus built from
fault injection on LocalNet (known true cause by construction: archive a contract, drop an
authorizer, unvet a package, exhaust traffic, …) and from production rejections of Rocky's
exchange, adjudicated blind. Metrics: coverage (share of corpus codes with a specific,
non-generic explanation) and precision of emitted diagnoses per error family. The
classifier abstains to a generic phase-level answer rather than guessing.

**Surfaces.** `canton-sim explain`, `canton-sim simulate`, `canton-sim contract`;
`canton-sim-server` (`POST /v1/explain`, `POST /v1/simulate`, `GET /v1/catalog[/{code}]`);
Rust crates. Milestone 3 adds the DPM component `dpm explain`, a TypeScript client, and
adapters so `dpm trace --command-id` and DPM Debug can call `explain` on a completion.

**Data and privacy.** Error bodies and the participant's own event lookup only; no ACS or
payload leaves the node; no dependence on mediator metadata. Diagnoses never include
data the acting parties could not read themselves.

**Delivered code.** `github.com/Rocky-DEX/Rocky.simulator` — Rust 1.88; 31 tests; CI
with clippy `-D warnings`; Apache-2.0; catalog generation script and provenance table in
`docs/error-catalog.md`.

### 3. Architectural Alignment

- Built on Canton's own error codes and annotations; no invented taxonomy where Canton
  already defines one — families reference official ids.
- Extends what exists: consumes Walnut's completion and prepared payloads; packaged as a
  `dpm` component per RFP 19; provides the integration contract that #297's reviewers
  identified so DPM Trace, DPM Debug and CI do not each rebuild failure diagnosis.
- Serves the roadmap priority "reduced developer friction" and the RFP 20 survey finding
  on transaction debugging.
- Governance references: CIP-0082 / CIP-0100.

### 4. Backward Compatibility

No backward compatibility impact. Read-only; unknown or renamed error codes still receive
a phase, the first sentence of the cause and generic guidance, so a Canton upgrade
degrades gracefully until the catalog is regenerated.

## Motivation

The Canton Foundation DevRel survey cited in the roadmap's RFP 20 note rated Transaction
Debugging & Observability lowest in Q1 (2.55) and tied-lowest in Q2 (3.26), "the
longest-standing unmet need in the dataset". The committee's review of #297 showed demand
for exactly this artifact and set the bar; that proposal closed for reasons unrelated to
the need.

Who benefits: every team that submits commands and every operator who reads participant
logs. Rocky's production integration met every failure class this tool explains —
`UNHANDLED_EXCEPTION` on custody assertions, `DAML_AUTHORIZATION_ERROR` on party-model
changes, `CONTRACT_NOT_FOUND` after version-bump patterns archived a contract,
`SEQUENCER_NOT_ENOUGH_TRAFFIC_CREDIT` under load, `PACKAGE_NOT_VETTED_BY_RECIPIENTS` on
MainNet — each debugged by hand. Node-service providers whose support load is rejection
triage, wallet teams surfacing errors to users, and DPM app teams in CI are the primary
adopters; we expect the majority of app teams to use the catalog or the API once it is
reachable from `dpm` and from `dpm trace`.

## Rationale

**Why an open catalog generated from sources.** Canton's error knowledge lives in Scala
annotations and changes per release. A script-generated, versioned JSON with provenance
is the only form that stays current and that other tools can depend on — the public-good
and sustainability expectations of the review process.

**Why a deterministic classifier with measured precision.** Reviewers of #297 asked for
a corpus and precision figures rather than claims. Determinism (same error, same catalog
version, same diagnosis) makes the tool safe for CI and support workflows; abstaining to a
phase-level answer avoids confident wrong diagnoses.

**Why extend rather than replace.** The component consumes Walnut's completion payloads
and is packaged per DPM conventions; it supplies the diagnosis that `dpm trace` and DPM
Debug currently render as raw text, instead of adding a third visualiser.

**Why pre-submit as well as post-hoc.** Running the same classifier on a `prepare`
rejection lets CI and wallets catch interpretation and authorization failures before any
traffic is spent, which neither a trace viewer nor a hosted simulator offers as a
key-less, node-local call.

**Alternatives considered.** Hand-maintained wiki of error codes — rejected, drifts per
release; LLM-based explanation — rejected, non-deterministic and unmeasurable; bundling
with the fee estimator — rejected per the single-objective guidance.
